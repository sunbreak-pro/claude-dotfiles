# コンテキスト効率化の横展開計画

- Status: ACTIVE
- 起点: fantasy_novel での実測（2026-08-13）と公式仕様の確認
- 粒度の原則: **本書は目的と優先順位だけを定める**。具体の設計・ファイル分割はプロジェクトごとに適否が変わるため、各プロジェクトのセッションで判断する。

## 根拠（公式仕様の要点）

- コンテキストを消費するのは「読まれたもの」だけ。置いてあるだけのファイルはコストゼロ。
- 毎セッション自動ロードされるのは CLAUDE.md 階層・`paths:` 指定のない rules・output style・スキルの description 1行・auto memory（先頭 200 行 / 25KB）。
- rules は frontmatter の `paths:` で「該当ファイルを触るときだけロード」にできる（注意: /compact 後は次に該当ファイルを読むまで再ロードされない）。
- スキル本文と参照ファイルは呼ばれたときだけロードされる（progressive disclosure）。
- 出典: code.claude.com/docs の context-window / memory / large-codebases / skills。

## 優先順位

### P1. 各プロジェクトの常駐層の点検（効果大・毎セッション効く）

- 目的: 「毎回机に載る固定費」を下げる。CLAUDE.md は 400 行規約を守り、MEMORY 系は台帳化（常駐は結論・状態タグ・ポインタだけ、詳細説明は docs/ や設計文書側へ）する。
- 目安: 常駐ファイル合計が 25KB を超えているプロジェクトから着手する。
- 先行例: fantasy_novel の MEMORY ダイエット（70KB → 30KB 前後）。

### P2. ダイジェスト方式の横展開（効果大・大量読み込みを置き換える）

- 目的: 「全体把握＝知識ベースの全読み」をやめ、「1枚の要約＋オンデマンド深掘り」に置き換える。要約は非正典のキャッシュとして置き、正典が常に優先。更新は正典変更とセットで節単位。
- 形はプロジェクト種別で変える: 小説 → 物語ダイジェスト／ソフトウェア → アーキテクチャ地図（構成・データフロー・主要契約の1枚）。
- 併せて既定にする運用: 全読みが避けられない仕事（監査・整合性チェック・初版生成）はサブエージェントに出し、メイン会話は結論だけ受け取る。
- 先行例: fantasy_novel の story-digest スキル（全体把握 約20万字 → 約1.1万字）。

### P3. グローバル rules の常駐最小化（効果中・全プロジェクトに波及）

- 目的: claude-dotfiles の常駐 rules を「毎セッション本当に要るか」で仕分ける。skill-management / agent-management / plan-mode-quality は path-scoped 化済みなので、残りに同じ物差しを当てる。
- 注意: 口調・応答方針のような挙動系ルール（tone 等）は常駐のままにする。paths: の /compact 後の再ロード制限も考慮する。

### P4. アーカイブ習慣（効果はトークンでなく誤読防止）

- 目的: 役目を終えたノート・古いログが Grep にヒットして現行設定と混ざる事故を防ぐ。区切りごとに archive 区画へ移す習慣を作る（トークン削減効果はほぼゼロと割り切る）。
- 恒常的に読ませたくないものは settings の `permissions.deny` の `Read()` ルールで遮断できる（.claudeignore 相当の機能は存在しない）。

### P5. ディレクトリ構造の再編は原則やらない

- 理由: 公式の per-directory 分割はモノレポ級の規模向け。中小規模リポジトリでは削減効果よりリンク切れ・参照崩れのリスクが勝つ。規模がモノレポ級になったときだけ再検討する。
