# デザインパターン

## カテゴリ概要

繰り返し現れる設計上の問題に対する定番の解法。
パターンの「名前」と「意図」を理解し、コード内で識別・適用する力を育てる。

## 関連カテゴリ

- **設計・アーキテクチャ**: パターンはアーキテクチャの中で局所的に使われる
- **コンパイル・ビルド**: 一部のパターンは言語機能（ジェネリクス、インターフェース）に依存する

## 難易度定義

### Lv.1 ★☆☆☆☆ — パターンを「知る」

**到達目標**: 「デザインパターン」が何かを理解し、日常的に使っているパターンを認識できる

**理解すべきこと:**
- デザインパターンとは何か（問題-解法-結果の組）
- なぜパターンが必要か（共通語彙、再発する問題への定番解法）
- 日常的に使われるパターン: コールバック、イテレータ、モジュール

**クイズ例:**
- 「`array.map(fn)` はどのような考え方に基づいているか？」
- 「import/export で分割する目的は何か？」

---

### Lv.2 ★★☆☆☆ — 基本パターンを「識別する」

**到達目標**: 生成・構造・振る舞いの3分類を理解し、基本的なパターンをコード内で見つけられる

**理解すべきこと:**
- GoFパターンの3分類（生成・構造・振る舞い）
- Singleton: グローバル状態管理、なぜ慎重に使うべきか
- Observer: イベントリスナー、Pub/Sub の原型
- Factory: オブジェクト生成の抽象化
- Strategy: アルゴリズムの切り替え

**クイズ例:**
- 「このコードは何パターンに該当するか？」（実際のコードを提示）
- 「`addEventListener` はどのパターンの実装か？」
- 「なぜここで new を直接使わず Factory を経由しているのか？」

---

### Lv.3 ★★★☆☆ — パターンを「適用する」

**到達目標**: 問題に対して適切なパターンを選択し、実装できる。アンチパターンも認識できる

**理解すべきこと:**
- Repository パターン: データアクセスの抽象化
- Decorator パターン: 既存機能の動的な拡張
- Adapter パターン: インターフェースの変換
- Middleware パターン: パイプライン処理
- アンチパターン: God Object、Spaghetti Code、Golden Hammer
- SOLID原則との関係

**クイズ例:**
- 「この API クライアントに Adapter パターンを適用してリファクタリングせよ」
- 「このコードはどのアンチパターンに該当するか？どう改善するか？」
- 「ミドルウェアチェーンの実行順序を追跡し、各ミドルウェアの責務を説明せよ」

---

### Lv.4 ★★★★☆ — パターンを「組み合わせる」

**到達目標**: 複数パターンの組み合わせや、パターンのトレードオフを理解し、過剰適用を避けられる

**理解すべきこと:**
- パターンの組み合わせ（例: Factory + Strategy、Observer + Mediator）
- パターンの過剰適用（Over-engineering）の判断基準
- 関数型プログラミングにおけるパターンの再解釈（高階関数、モナド）
- 言語固有のイディオムとの関係（例: Python の Decorator は GoF の Decorator とどう違うか）
- DI（依存性注入）コンテナの仕組みと設計意図

**クイズ例:**
- 「この設計でパターンを適用しすぎている箇所はあるか？簡略化案を示せ」
- 「Factory + Strategy の組み合わせを使って、この機能を拡張可能にせよ」
- 「DI コンテナがない場合、この依存関係をどう管理するか？」

---

### Lv.5 ★★★★★ — パターンを「超える」

**到達目標**: 既存パターンの限界を理解し、プロジェクト固有の設計慣習を体系化できる

**理解すべきこと:**
- ドメイン固有のパターン（例: Saga パターン、Circuit Breaker）
- リアクティブプログラミングパターン
- イベントソーシングにおけるパターン
- パターンカタログの自作（プロジェクトの「こうやる」集）
- パターンの歴史的文脈と進化

**クイズ例:**
- 「このプロジェクトで繰り返し使われている独自の設計パターンを抽出し、名前を付けて文書化せよ」
- 「Circuit Breaker を導入すべき箇所を特定し、実装方針を示せ」
