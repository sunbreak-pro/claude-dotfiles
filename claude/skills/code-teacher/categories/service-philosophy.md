# サービスの思想

## カテゴリ概要

ソフトウェアを「サービス」として提供する際の設計哲学と原則。
「なぜこの API 設計なのか」「なぜこの認証方式なのか」の背景にある思想を理解する力を育てる。

## 関連カテゴリ

- **要件定義**: ビジネス要件がサービス設計の根拠
- **設計・アーキテクチャ**: サービス思想がアーキテクチャの選択に影響
- **ネットワーク**: API 設計はネットワークプロトコルの理解が前提

## 難易度定義

### Lv.1 ★☆☆☆☆ — サービスを「使う」

**到達目標**: API を使う側として、ドキュメントを読んでリクエストを送れる

**理解すべきこと:**
- API ドキュメントの読み方（エンドポイント、パラメータ、レスポンス例）
- 認証と認可の違い（ログインできる vs 権限がある）
- API キーの扱い方（なぜ .env に入れるか、Git にコミットしてはいけない理由）
- レート制限の概念（429 Too Many Requests の意味）
- SDK とは何か（API を楽に使うためのラッパー）

**クイズ例:**
- 「この API ドキュメントを読んで、ユーザー一覧を取得するリクエストを書け」
- 「API キーを GitHub にプッシュしてしまったら、最初に何をすべきか？」

---

### Lv.2 ★★☆☆☆ — API を「設計する」基礎

**到達目標**: RESTful な API のエンドポイント設計と命名規則を理解し、基本的な設計ができる

**理解すべきこと:**
- RESTful 設計の基本原則（リソース指向、名詞ベースのURL）
- エンドポイントの命名規則（`/users/:id` vs `/getUser`）
- ステータスコードの適切な使い分け（201 Created, 204 No Content, 422 Unprocessable Entity）
- リクエスト/レスポンスの一貫性（ページネーション、エラーフォーマット）
- 認証フロー: API キー、Bearer Token の基本

**クイズ例:**
- 「このAPIの URL 設計で RESTful でない部分はどこか？改善案を示せ」
- 「新しいリソース『注文（order）』の CRUD エンドポイントを設計せよ」
- 「このエラーレスポンスの問題点は何か？」

---

### Lv.3 ★★★☆☆ — サービスの「品質を考える」

**到達目標**: 12-Factor App の原則を理解し、認証・認可の設計、バージョニング戦略を実践できる

**理解すべきこと:**
- 12-Factor App の主要な原則（設定の外部化、ポートバインディング、使い捨て性）
- OAuth 2.0 / OIDC の基本フロー（Authorization Code, Client Credentials）
- JWT の構造と検証の仕組み（Header, Payload, Signature）
- API バージョニング戦略（URL, Header, Content Negotiation）
- べき等性（Idempotency）の設計と Idempotency Key
- 入力バリデーション戦略（クライアント側 vs サーバー側）

**クイズ例:**
- 「12-Factor App の原則のうち、このプロジェクトで守られていないものを特定せよ」
- 「OAuth 2.0 の Authorization Code フローを図示し、各ステップの目的を説明せよ」
- 「この API にべき等性を保証する仕組みを追加するにはどうすべきか？」

---

### Lv.4 ★★★★☆ — サービスの「成長を設計する」

**到達目標**: マルチテナンシー、後方互換性、SLA の設計ができる

**理解すべきこと:**
- マルチテナンシーの3モデル（DB分離, スキーマ分離, 行レベル分離）
- 後方互換性の維持戦略（Additive Change Only、Deprecation Policy）
- SLA/SLO/SLI の定義と設計（Error Budget の考え方）
- Webhook の設計（リトライ、冪等性、署名検証）
- API ゲートウェイの役割（認証集約、レート制限、ルーティング）
- RBAC（Role-Based Access Control）vs ABAC（Attribute-Based）

**クイズ例:**
- 「このサービスに SLO を設定するとしたら、どの指標をどの水準で定義するか？」
- 「マルチテナンシーを導入する場合、データ分離モデルの選択基準は？」
- 「API の破壊的変更を安全にリリースする計画を立案せよ」

---

### Lv.5 ★★★★★ — プラットフォームを「構想する」

**到達目標**: API エコシステムの戦略設計、開発者体験（DX）の最適化、技術的なプロダクト戦略を立案できる

**理解すべきこと:**
- API as a Product（API をプロダクトとして設計する思想）
- 開発者体験（DX）の設計原則（SDK、ドキュメント、Sandbox環境）
- Platform Engineering（社内プラットフォームの設計思想）
- イベント駆動アーキテクチャの設計哲学（EDA）
- ドメインイベントとインテグレーションイベントの使い分け
- 技術戦略とビジネス戦略の整合

**クイズ例:**
- 「このサービスを外部開発者に公開する場合の API 戦略を設計せよ」
- 「社内向けプラットフォームとして提供する場合の DX 改善案を3つ提案せよ」
