# Code Refactoring

言語非依存のリファクタリングワークフローを提供する汎用スキル。

## ワークフロー

```
1. スコープ特定 → 対象ファイル/関数を把握
2. 種別判定 ↓
   ├─ 命名規則の統一     → 「命名規則ワークフロー」
   ├─ 重複コード除去     → 「DRYワークフロー」
   ├─ コンポーネント共通化 → frontend-refactoring スキルを参照
   ├─ 関数/クラス分割    → 言語固有スキルを参照
   └─ パフォーマンス最適化 → 言語固有スキルを参照
3. 変更適用 → 段階的に適用、各段階でテスト実行
```

言語固有スキルが `<project>/.claude/skills/<lang>-refactoring/` に存在する場合、
分割基準やパフォーマンスパターンはそちらを参照すること。存在しない場合は
`references/lang-specific-patterns.md` の一般指針に従う。

## 命名規則ワークフロー

対象コードの命名を一貫させる手順:

1. 対象スコープ内の変数・関数・クラス・定数名を列挙
2. プロジェクトの既存コードから支配的な命名規則を推定（言語固有スキルがあればそちらを優先）
3. 不統一な箇所を特定し、修正案を提示
4. 影響範囲を確認（import/export、テストコード、設定ファイル）
5. 一括置換を適用

**判断基準:**

- プロジェクト既存コードの規則 > 言語のデファクト規則
- 略語は避けるが、広く認知された略語（id, url, api, db）は許容
- ブール値は is*/has*/can\_ 等の接頭辞で意図を明示

## DRYワークフロー

重複コードを検出・統合する手順:

1. 類似コードブロックを検出（完全一致だけでなく構造的類似も対象）
2. 重複の種類を分類:
   - **完全重複**: そのまま共通関数へ抽出
   - **パラメトリック重複**: 差異部分を引数化して共通関数へ抽出
   - **構造的重複**: テンプレートメソッドパターンまたは高階関数で抽象化
3. 対処の優先順位を決定:
   - **高優先**: 頻繁に変更される箇所の重複（変更漏れリスク）
   - **高優先**: バグ修正が必要な重複（1箇所修正して他を忘れる危険）
   - **中優先**: 新機能追加時に必ず触る箇所の重複
   - **低優先**: 安定しており変更頻度が低い箇所の重複
4. 抽出先を決定（同一ファイル内 / ユーティリティモジュール / 共通ライブラリ）
5. テストが既存の場合は維持、ない場合は抽出後の関数にテストを追加

**抽出しない方が良い場合:**

- 重複が2箇所のみで、今後増える見込みがない
- 抽出すると関数の引数が過度に複雑になる
- ドメインが異なり、偶然同じコードになっているだけ

**抽出の判断基準:**

| 条件                                        | 判断                             |
| ------------------------------------------- | -------------------------------- |
| 3箇所以上で同一パターン                     | 抽出する                         |
| 2箇所のみ、今後増加の見込みあり             | 抽出する                         |
| 2箇所のみ、増加見込みなし                   | 放置（コメントで類似箇所を記録） |
| ドメインが異なり偶然の一致                  | 放置                             |
| 抽出すると引数/パラメータが過度に複雑になる | 放置                             |
| 抽出により型安全性が低下する                | 放置                             |

**移行リスクの確認:**

抽出を決めた場合、着手前に以下を確認:

- テストカバレッジ: 対象箇所にテストがあるか（なければ先にテスト追加）
- 依存範囲: 影響箇所が5つ以上なら段階的移行を検討
- 型安全性: 抽出後も型チェックで破壊的変更を検出可能か

## コンポーネント共通化

React/フロントエンドのコンポーネント・フック・コンテキスト共通化は `frontend-refactoring` スキルを参照すること。

## リファクタリングプラン出力フォーマット

リファクタリング計画の作成を求められた場合、以下のセクションを含めること。
小規模（単一ファイル内）ではフェーズ計画・移行戦略は省略可。

### テンプレート

```markdown
# [対象の概要]

## 背景・動機

なぜこのリファクタリングが必要か。技術的負債、可読性、拡張性等の観点。

## 分析結果

| パターン | 出現箇所    | 種別                       | 影響度   |
| -------- | ----------- | -------------------------- | -------- |
| ...      | ファイル:行 | 完全/パラメトリック/構造的 | 高/中/低 |

## フェーズ計画

### Phase N: [フェーズ名]

- **前提条件**: なし / Phase M の完了
- **リスク**: [高/中/低] — [理由]
- **影響**: [定性的な改善効果]
- **対象**: [ファイル一覧]
- **手順**: [具体的ステップ]

## 移行戦略

段階的移行か一括移行か。旧コードとの共存期間の方針。

## 検証

- テスト戦略
- ロールバック手順（各フェーズは独立してリバート可能か）
```

### 留意事項

- フェーズは依存関係に基づき順序付け（独立フェーズは並行実施可能と明記）
- リスク評価は「変更の広がり」「テストカバレッジ」「ドメイン知識の必要性」で判断

## 汎用コードスタイル原則

言語によらず適用する原則:

- **早期リターン**: ネストを減らすためガード節を使用
- **マジックナンバー除去**: 数値/文字列リテラルは定数に抽出
- **単一責務**: 1関数1責務を基本とする（分割基準の詳細は言語固有スキル参照）
- **コメント**: Why（なぜ）を書く。What（何をしているか）はコード自体で表現する

## プロジェクト固有スキルの生成

新しいプロジェクトに言語固有のリファクタリングスキルを追加する場合:

```bash
bash ~/.claude/skills/code-refactoring/scripts/init_lang_refactoring.sh <lang> <project-root> [project-name]
```

対応言語: python, typescript, javascript, rust, go, java, cpp, ruby, swift, kotlin

スクリプトは以下を実行する:

1. `<project>/.claude/skills/<lang>-refactoring/SKILL.md` を言語プリセットから生成
2. `~/.claude/skills/refactoring-collection/` にシンボリックリンクを作成

生成後、プロジェクト固有の規約に合わせて SKILL.md を編集すること。

## 言語固有の考慮事項

関数/クラスの分割判断やパフォーマンス最適化は言語ごとに大きく異なる。
詳細は `references/lang-specific-patterns.md` を参照。
